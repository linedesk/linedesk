# Linedesk architecture

Status: decided, 2026-11-10. This is the single source of truth for how Linedesk works. Why each piece was chosen (research, spikes, costs) lives in [stack.md](stack.md); product decisions in [decisions.md](decisions.md); the plan and workstreams in [plan.md](plan.md).

## 1. What v1 does

A US service business (demo: a plumber in Portland) keeps its existing phone number and forwards calls it can't take to Linedesk. An AI assistant ("Maya" by default, renamable) answers, understands the request, books appointments into the business's calendar, takes messages, escalates emergencies to a person, and turns every call into an item in a keyboard-first inbox.

v1 = phone + calendar. It is built on the platform foundation (action registry, local-first sync, provider adapters) so WhatsApp, SMS and email can follow without rework.

Out of scope for v1: messaging channels, outbound campaigns, multi-location routing, enforced compliance guardrails (kept configurable, see §10).

## 2. Principles that shape the architecture

1. **One action, every surface.** Every user or agent action is defined once and exposed as UI command, REST endpoint, MCP tool, ⌘K entry and voice-agent tool.
2. **Instant and offline.** The UI applies every action locally at once and syncs in the background; it keeps working offline.
3. **Adapters with a recommended default.** Telephony, speech, LLM, calendar and sync providers are swappable behind interfaces; setup always suggests one.
4. **Easy to self-host, able to scale.** `docker compose up` gives a working install; the same images scale horizontally.
5. **Open-source ready.** No secrets or customer data in the repo; paid-only code lives in `ee/`.

## 3. System overview

```
 Caller ──PSTN──▶ Business number ──(conditional forward)──▶ Linedesk DID (Telnyx, default)
                                                                   │ SIP
                                                                   ▼
                                                       LiveKit SIP service
                                                                   │ joins room
                                                                   ▼
                                ┌─────────── LiveKit room (one per call) ───────────┐
                                │  caller (SIP participant)                          │
                                │  voice agent (LiveKit Agents, TypeScript)          │
                                │  owner (optional: browser or phone when taking over)│
                                └────────────────────────────────────────────────────┘
                                        │ agent tools = registry actions
                                        ▼
  Web app (Vite SPA) ─commands─▶  API (Hono): action registry ──▶ Postgres ◀── worker (pg-boss jobs)
   local store + outbox  ◀─reads──  read-sync adapter (Electric)       │
                                        │                              └── object storage (recordings)
                     REST + OpenAPI · MCP server · webhooks
                                        │
                         Google Calendar · Microsoft Graph
```

## 5. Action registry

Every action is defined once:

```ts
defineAction({
  name: 'call.markDone',
  input: z.object({ callId: z.string() }),
  permission: 'call:write',
  apply: (store, input) => { /* optimistic local change, runs in the browser */ },
  handler: async (ctx, input) => { /* authoritative, runs on the server, writes Postgres */ },
  event: 'call.done',
})
```

From that definition we generate:

| Surface | Generated |
|---|---|
| Web app | instant local mutation (`apply`) + outbox command, ⌘K entry |
| REST | `POST /v1/actions/<name>` + OpenAPI spec |
| MCP | one tool per action, same schema and permission |
| Voice agent | tool with the same schema (e.g. `appointment.book`) |
| Events | internal event per action; an assistant's webhook at call start, during the call (its lookups) and after the call (docs/webhooks.md) |

Reads are defined once as named queries and exposed to the UI (live via sync), REST and MCP.

### v1 actions (initial set)

| Area | Actions |
|---|---|
| Calls | `call.markDone`, `call.markNotDone`, `call.remind`, `call.clearReminder`, `call.markRead`, `call.markUnread`, `call.assign`, `call.callBack`, `call.delete` |
| Live call | `call.listen`, `call.takeOver`, `call.hangUp` |
| Bookings | `calendar.findSlots`, `appointment.book`, `appointment.reschedule`, `appointment.cancel` |
| Contacts | `contact.lookup`, `contact.update` |
| Agent-only | `call.takeMessage`, `call.transfer`, `call.end`, `call.flagUrgent` |
| Settings | `assistant.update`, `appointmentType.upsert`, `calendar.connect`, `calendar.setFlags`, `phoneNumber.setup`, `phoneNumber.verifyForwarding` |

## 6. Sync: "commands up, data down"

- **Writes:** every registry call from the web app is a command. The client applies it to its local store immediately, persists it in an IndexedDB outbox and replays it in order to `POST /v1/actions/<name>` (idempotent per command id). The server is authoritative; a rejection rolls the local change back and shows a toast.
- **Action answers** (`apps/api/src/run-action.ts`): 200 `{ ok: true, rows, data? }`; 403 `{ ok: false, error, code: "forbidden" }` when this caller may not do it (a missing permission, an owner-only rule, not while signed in as another user or with an API key; handlers throw `Forbidden`); 409 `{ ok: false, error }` when the data's state does not allow it (`Reject`: not found, the last owner); 422 for invalid input, said as plain sentences that name fields as people say them ("Account SID", not `values.account_sid`). A replayed command answers with the status of its first answer. Input fields an action does not take: 422 for API keys and other callers; dropped with a warning in the API log for the web app's sessions and the voice agent, because the outbox replays commands stored by an older release after a deploy and the agent can run one release behind the API.
- **Cross-site writes:** every non-GET request under `/v1` signed in by the session cookie (no `Authorization: Bearer`) must come from the web app's origin (`Origin` equal to `WEB_ORIGIN`) and be `application/json`, else 403 `cross_site_refused` (`apps/api/src/csrf.ts`, before every `/v1` route). The cookie is SameSite=Lax, so a page on another subdomain of the same site would still send it, and a `text/plain` POST needs no preflight. API keys and the agent (Bearer) are not affected; Better Auth checks the Origin of `/api/auth/*` itself.
- **Reads:** Postgres → local store through our `ReadSyncAdapter` interface, scoped per workspace and permission. Default adapter: Electric. Swapping the provider touches only the adapter file, not the UI. Electric itself has no notion of workspaces, so only the API may reach it: it runs with `ELECTRIC_SECRET`, which the API adds to every proxied shape request (`GET /v1/shape/<table>`), and in the compose stack Postgres and Electric are only on the internal `backend` network, which only the `api` service joins (the agent, LiveKit, SIP, egress, Redis and Caddy are not on it).
- **Offline:** reads and queued writes survive a reload; a service worker serves the app shell.
- **Live calls:** transcript segments are rows like any other, so they arrive through the same read sync (target < 1 s).

## 7. Call lifecycle

1. **Ring.** The caller dials the business. If nobody answers within N rings (or the line is busy), the carrier forwards to the workspace's Linedesk number.
2. **Ingress.** The provider sends the call over SIP to LiveKit SIP. A dispatch rule maps the DID to a workspace and creates room `call_<id>`. The API creates `Call { status: live }`; it appears at the top of Needs you with a live indicator.
3. **Caller lookup.** First tool: `contact.lookup(phone)` → contact, past calls, upcoming bookings, so the assistant knows a returning customer (it does not greet them by name).
4. **Greeting.** Configurable greeting; AI disclosure on by default (configurable, §10).
5. **Conversation.** The agent follows the assistant config (About the business, booking types, urgent and transfer rules). Its tools are registry actions:

   | Tool | Effect |
   |---|---|
   | `contact.lookup` | Contact + history |
   | `calendar.findSlots(type, window)` | Free slots = working hours ∩ free/busy of conflict calendars − buffers − min notice |
   | `appointment.book` / `.reschedule` / `.cancel` | Writes the calendar event, stores `Booking`, links the call |
   | `call.takeMessage` | Adds an action item to the call |
   | `call.flagUrgent` | Marks urgent (e.g. "leak", "gas smell"), triggers notification |
   | `transfer_call` → `call.transfer(to, name, urgent, result)` | Warm transfer to the transfer contact whose condition fits (see below); when nobody accepts, the contact's fallback: a message marked urgent, a message, or the next contact that fits |
   | `call.end` | Hangs up politely |

   **Limits on one call** (what a caller can make the assistant spend or send): at most 3 messages (`MESSAGES_PER_CALL`, each one is a push; only next steps with `kind: 'message'` count, so a note the API adds takes no slot) and 2 bookings (`BOOKINGS_PER_CALL`) per call, counted under a per-call advisory lock; members are not limited. `calendar.findSlots` on a call looks only in the calendars of the assistant that answered it. Links in a booking's reason are replaced with "[link removed]" before it reaches the calendar. A call flagged urgent while it ran stays urgent after the summary, and is never filed as spam (it becomes a callback). Test calls from the web app: 6 in 10 minutes and 20 a day per user over all their workspaces, and 200 a day on the install (`TEST_CALLS_PER_DAY`; reaching it logs an `ALERT` line). They count the tokens issued, used or not: each one is a row in the command log (`assistant.testCallToken`, its room, never the token), counted and written under one install-wide advisory lock, so neither a burst of tokens nor several API processes get past them. A test room opens at most one call.
   **Monthly spending cap** (`apps/api/src/spending-cap.ts`): off by default; an instance admin sets one per workspace in Admin › Workspaces (`workspace.setSpendingCap`, USD, stored as `organization.spending_cap_cents`; empty: no cap). The measure is the estimated cost of the workspace's calls this UTC month with the overview's rates (`costEstimate` in `admin-overview.ts`; deleted calls count, sample calls do not, a live call counts once it finished). Once reached, `call.start` answers `overCap` (and `blocked`, for older agents): the call is filed as missed with "Call back" and the usual push, and the agent says one fixed line in the assistant's voice ("we can't take your call right now, we'll call you back") and hangs up, so the caller never hears silence and the cap costs a few seconds per call. Test calls are refused. Owners and instance admins get an email at 80 % and at 100 % (pg-boss job `spending.capAlert`, once per workspace, month and level in `spending_cap_alerts`; a new cap starts the month's emails over). Calls already running when the cap is reached go on.

   Every tool call is also written to the transcript as a system event ("Checked availability · 3 slots").

   **Transfer contacts** (per assistant, `assistants.transfers`, an ordered list edited as a whole with `assistant.update { transfers }`; Settings › Assistant › Transfers): each contact has a name (unique in the list: the assistant picks by it), a number (null: none yet, the contact is inactive; checked by `onCallNumberProblem`: US landlines and mobiles only (libphonenumber's US region, so not Canada, the Caribbean or territories), never premium rate (900, 976 behind any area code), 500/700, toll-free or N11; never a Linedesk number or a line forwarding to one), a plain-language `condition` ("The caller asks to speak to a person", "Urgent: burst pipe, gas smell, no heat", "Billing questions"), `hours_only` (not while the business is closed), `ring_seconds` (10–60, default 25), `if_no_answer` (`message_urgent | message | next`) and `enabled`. A new assistant starts with one contact, "The caller asks to speak to a person", without a number (inactive until one is set); a copied assistant starts from that default too. Migration 0046 turned the old single on-call number (`transfer_urgent`, `transfer_number`, `transfer_hours_only`, kept until the next release, then dropped) into the first contact, "Urgent: an emergency that needs a person right now". The agent takes the contacts that are on, have a number and are not limited to hours while closed (`transferContactsFor`), and gives the assistant `transfer_call` from the start of the call when there is one (`transferFrom` in `apps/agent/src/worker.ts`, `apps/agent/src/transfer-tool.ts`): how to dial each contact is looked up right away, but nothing is dialled until the assistant uses the tool, once a contact's condition fits. A contact that cannot be dialled on the call (no outbound trunk, a phone call test) counts as not answered: the next one is tried only when its `if_no_answer` is `next`. The prompt lists them in order with their conditions; the tool takes every contact whose condition fits, and `transferPlan` tries them in the owner's order: a contact whose fallback is `next` hands over to the next one that fits (at most 3 tries a call); when nobody accepts, the last one's fallback applies (`next` with nobody left: a message marked urgent). Before each ringback the caller hears a fixed line naming the contact ("I'm trying to reach Mike now…", then "Mike can't take the call right now. Let me try Sarah…"); when nobody accepts, the assistant tells the caller and takes a message. `call.transfer` records the contact's name (`calls.transfer_name`) and marks the call urgent unless `urgent: false` (a fallback that is a plain message). Each try has its own consult room (`<room>-oncall`, `<room>-oncall-2`, …).

   **Warm transfer**, how one try works: The agent first asks the API with `call.transfer` `dialing`, which keeps the workspace's limits (6 transfers started an hour, one on-call leg ringing or connected at a time, under a per-workspace advisory lock); a refusal means a message. The caller hears a fixed "I'm trying to reach …" line, then a ringback tone; the agent joins a consult room `<room>-oncall` and dials the on-call number into it with `CreateSIPParticipant` through the LiveKit outbound trunk `linedesk-outbound` (`setup-sip --outbound`; Telnyx credential connection of the same name, caller ID = the business's Linedesk number), ringing for the contact's ring time (default 25 s). A small voice session there (speech recognition and voice, no LLM) says "Urgent call from <name or number> about <topic>." ("Call from …" when the contact's fallback is a plain message) Press 1 or say yes…" (not interruptible), twice at most, and only after it has played counts key 1/2 or a short clear yes/no (at most six words, nothing that sounds like a voicemail greeting), so a voicemail is never put through. On yes the call's recording is stopped (the conversation with the on-call person is not recorded; if it cannot be stopped, nobody is put through and the assistant takes a message) and the agent bridges the audio of both rooms itself (`audio-bridge.ts`) and stays silent; the call ends when either side hangs up, outcome `transferred`. On no, no decision (voicemail) or no answer the consult room is deleted, which hangs up the on-call phone, and the assistant takes a message. `call.transfer` stores `transfer_to` and `transfer_result` (`connected | not_answered | declined | failed`) and marks the call urgent; the call view shows "Transferred to …" or "Transfer not answered". Why the agent bridges instead of LiveKit's `MoveParticipant` (Cloud only: "not implemented" on self-hosted LiveKit 1.13) or SIP REFER (cold, carrier-dependent, the call leaves LiveKit): decisions.md. Closing the consult room is registered as a shutdown callback before anything is dialled, and a dial stops waiting as soon as the caller hangs up. Test calls never dial an on-call phone: on a browser test call a simulated person accepts and says it is a test (`TEST_CALL_ON_CALL_LINE`, the API sets `simulateTransfer` in the test room's metadata), phone call tests (from `CALL_TEST_FROM`) cannot dial anyone, and the `transfer-*` call-test scenarios refuse `--phone` and use a simulated on-call person (the one exception is the live transfer test below, an explicit opt-in). The `linedesk-outbound` Telnyx voice profile is US-only (allowed destinations `US` only; created on the global plan, the only one Telnyx accepts for new profiles), set again on every `setup-sip --outbound`, and setup fails if Telnyx does not keep the list at `US`; Linedesk only manages Telnyx objects named `linedesk-*`.

   **Live transfer test** (operators, over real phone lines; a few cents per call). It needs one more number in the install's Telnyx account (not connected to any workspace), the test on-call number, answered by the on-call responder (`apps/agent/src/oncall-responder.ts`): the worker plays the on-call person, waits for the briefing, says "Yes, put them through." and presses 1, then says to the caller "Hi, this is Mike, the on-call plumber…" and hangs up, so the test caller's transcript proves the bridge. Setup, once: buy the number and point it at LiveKit SIP like any other (Telnyx connection `linedesk-livekit`), then `setup-oncall-test <on-call number> [--answer accept|decline|no-answer]` (its own inbound trunk and dispatch rule `linedesk-oncall-test`, same carrier address list; never pass this number to `setup-sip`), and `setup-sip --outbound <every business number>` once for the `linedesk-outbound` trunk. Per run: add a transfer contact with the on-call number to the test workspace's assistant (condition: urgent); set `CALL_TEST_ONCALL=<on-call number>` in the agent's env and recreate the agent container; `call-test transfer-accepted --phone` (from `CALL_TEST_FROM` to `CALL_TEST_TO`). With `CALL_TEST_ONCALL` set, a phone call test may be put through to exactly that number and no other (`liveTransferTestAllows`), and call-test allows `--phone` for the `transfer-*` scenarios; without it both stay refused. Check: the test caller's lines in the agent log ("business: Hi, this is Mike, the on-call plumber…"), the call shows "Transferred to …", the recording ends at the bridge, and no `call-*`, `*-oncall` or `oncall-test-*` room is left after hang-up (`lk room list`). Afterwards: switch that contact off again (keep the number), unset `CALL_TEST_ONCALL` and recreate the agent container (`docker compose up -d agent`; wait until the new worker is registered before the next call). The trunk, rule and number can stay for the next run; to tear the test down, `setup-oncall-test --remove` deletes the trunk and dispatch rule (calls to the number then reach no agent), and the number is released in the Telnyx portal. The on-call number may not be a Linedesk number or a line that forwards to one: `assistant.update` refuses both.
6. **Live view.** Transcript streams to the web app. A live call shows "Live" in the inbox and, opened, a card with **Listen** (L) and **Take over** (⇧T) for any signed-in member of the workspace (owners, admins, members; not API keys, the agent or an instance admin signed in as someone). Both are read-only actions (`call.listen`, `call.takeOver`, `apps/api/src/live-call.ts`) that check the call is live and in the member's workspace (another workspace's call is "not found") and sign a LiveKit token for that call's room only, valid 60 s for joining, no data messages and no changing its own attributes. Listen: hidden, cannot publish anything; the browser plays the call and shows the lines still being spoken (the agent's transcription streams, as in the test call). Take over: cannot publish at first either, and carries the member's name in the participant attribute `linedesk.takeOver`, which only the API can set. Another member's take-over holds the call for 90 s (time to join and hand over; the same member may rejoin; refused while a warm transfer is ringing or connected); after that the agent decides: the first member to join gets the call, anyone later or anyone it cannot hand over to is told `refused` and removed from the room (`removeParticipant`). The agent (`apps/agent/src/take-over.ts`) stops listening to the caller, stops the recording (fail closed: if it cannot, it sets `linedesk.handOff=<sid>:refused` on itself and carries on), says "I'm putting you through to <name> now.", mutes itself, grants the member microphone-only publishing (`updateParticipant`) and sets `linedesk.handOff=<sid>:ready`; only then can the browser turn the microphone on. A member disabled during a call keeps their connection until it ends (tokens are checked only on joining). From there the call is like a connected warm transfer: not recorded or transcribed, no silence prompts or assistant time limit, outcome `transferred`, the transcript shows "<name> took the call over". The member's Hang up ends the call; a dropped connection gets 15 s to rejoin. The browser keeps the session outside the call view (`apps/web/src/call/liveSession.ts`), so moving to another call does not drop the caller. Each first listen-in per member and each take-over is a `call_events` row (`listened`, `took_over`). Hand back to the assistant and dialling the member's phone are not built.
7. **Hang-up.** Recording finalised to object storage.
8. **Post-call job.** An LLM pass returns structured JSON: `title`, `summary`, `outcome`, `urgency`, `intent`, `actionItems[]`, `fields[]`, spam score. The call moves to the right view.
9. **Notify.** Email per finished call and Web Push (opt-in per member and browser; VAPID keys from env; one notification per call that a flagged-urgent, message-taken or finished push updates; payload is who called plus, if opted in, one line); daily digest for the rest later. See README, Push notifications.

Target latencies: answer < 1 ring after forward, first agent word < 1.2 s, turn latency < 800 ms, call summary ready < 10 s after hang-up.

## 8. Phone setup and calendar

**Phone number modes** (`PhoneNumber.mode`):

- `forward_conditional` (default): unanswered/busy calls go to Linedesk. Setup = dialing a carrier code (Verizon `*71<number>`, AT&T/T-Mobile `**004*<number>#`), verified with a test call.
- `forward_all`: Linedesk answers every call.
- `new` / `ported`: a new local number, or the existing number ported in.

**Connecting a number** (`phoneNumber.setup`, owner or admin, carrier from `TELEPHONY_PROVIDER`):

- `{ e164 }` attaches a number that already exists in the carrier account and buys nothing; a number that is not there is rejected.
- `{ areaCode, purchase: true }` or `{ e164, purchase: true }` buys a number. This costs money and happens only with `purchase: true`; if a later step fails, the bought number is released.
- Either way the carrier is pointed at LiveKit SIP (`LIVEKIT_SIP_ENDPOINT`) and the `phone_numbers` row is stored. Afterwards `pnpm --filter @linedesk/agent setup-sip <all numbers>` makes LiveKit accept the number (from the carriers' signaling addresses only, see below).

**Own carrier account** (Settings › Phone numbers › Carrier; owners and admins, `settings:write`). By default a workspace uses the install's carrier (Admin › Providers). It can bring its own Twilio or Telnyx account instead:

- `workspace_settings.carrier`: `default`, `twilio` or `telnyx`. The credentials are `provider_settings` rows with the workspace's id: Twilio Account SID plus either an API key (SID and secret, recommended) or the auth token; Telnyx an API key. AES-256-GCM with `SECRETS_KEY`, each ciphertext bound to `workspace:<id>:<carrier>.<field>`, so a value copied into another workspace's row does not decrypt. Without `SECRETS_KEY` saving is refused.
- `carrier.set` replaces the credentials as a whole (switching carrier or back to `default` deletes the old ones); its `values` are `sensitive`, so the command log keeps them as `[redacted]`. The browser calls it directly, not through the outbox, so credentials are never kept in IndexedDB. `carrier.get` returns the carrier, which fields are set, the Account SID and API key SID (not secret) and the last four characters of a stored secret of 12 characters or more; never a secret. Members and the agent token get 403.
- `carrier.test` ("Test connection", run after every save) only reads: it lists up to 20 numbers of the account (`TelephonyProvider.listNumbers`) with an 8 second timeout, at most 10 per workspace in 10 minutes. 401/403 answer with a fixed text; other errors carry the carrier's text with every credential removed. Stored values that cannot be decrypted (another `SECRETS_KEY`) are reported as "enter them again", never with the operator's detail.

- Concurrency: `carrier.set`, `phoneNumber.setup` and `phoneNumber.release` first take a per-workspace transaction lock (`pg_advisory_xact_lock(hashtext('carrier:<workspace id>'))`, `lockWorkspaceCarrier`), so the carrier cannot be switched while a number is being set up or released with it (setup holds its transaction across the carrier requests).
- Numbers already in the install's account: only an instance admin may attach one to a workspace (`phoneNumber.setup` without buying, or with `purchase` for a number the account already has); other members buy a new number or bring their own account. `/v1/me` `phoneSetup.canAttach` tells the web app, which then offers only "Get a new number". The `workspace:create` CLI runs as the operator. Without a carrier (`dev`) and in the workspace's own account attaching is open to owners and admins.
- Buying on the install's account (the operator pays; sign-up is open): someone who is not an instance admin buys only by US area code (a typed number could be anywhere), and the API refuses a purchase when the workspace holds 2 numbers bought there or bought 2 in the last 30 days, when the user bought 2 there in the last day (all their workspaces), or when 10 were bought on the install in the last hour, and install-wide at 20 a day and 100 in 30 days (`NUMBER_PURCHASES_PER_DAY`, `NUMBER_PURCHASES_PER_30_DAYS`; reaching it logs an `ALERT number purchases` line). An API key cannot buy on the install's account. Everything that can refuse (assistant, workspace state, limits) is checked before the carrier is asked. Every purchase is logged in `number_purchases`, committed on its own before the carrier is asked, so it outlives a released number and a failed action: buying and releasing, or a purchase whose action fails afterwards, still counts (`apps/api/src/number-purchases.ts`). Purchases on the install's account run one at a time and setups in a workspace too (`pg_try_advisory_xact_lock`): one that comes meanwhile is refused at once ("Another number is being set up, try again in a moment") instead of holding a database connection while it waits; `phoneNumber.setup` also sets `lock_timeout` 5 s. The purchase log is written through its own pool of two connections (`ownCommitDb`), so it never waits for a connection of the main pool that the waiting transactions hold. Instance admins' purchases (`by_admin`), the workspace's own account and `dev` are not counted or limited.
- Numbers: `phoneNumber.setup` resolves the carrier per workspace (`telephonyForWorkspace`, `apps/api/src/workspace-carrier.ts`): the workspace's own account when it has one, else the install's. The number row stores which (`phone_numbers.carrier_account`: `workspace` | `install`), and `phoneNumber.release` releases or un-routes it only in that account: a `workspace` number with the workspace's own credentials (read by the number's own workspace id), an `install` number with the install's carrier. Numbers that were connected before a workspace brought its own account stay `install`. Attaching looks the number up in the workspace's account, so a number can only be added by the workspace whose account has it (and `e164` is unique across the install).
- While numbers are in the workspace's own account, `carrier.set` refuses another carrier or `default` ("Disconnect it first"), and new credentials for the same carrier must find every one of those numbers with the same carrier id (read-only look-ups), so a number is never managed with credentials of an account it is not in.
- `/v1/me` `phoneSetup` reports the workspace's carrier (own account, else the install's); Settings › Phone numbers lets owners add numbers with their own account even when the install has no carrier.
- Webhooks of a workspace's account verify with that account's own key: the adapter built from the workspace's credentials (`ownCarrierProvider`) checks Twilio signatures with the workspace's auth token (refused with only an API key: Twilio signs with the auth token) and Telnyx signatures with the workspace's optional webhook public key, never the install's. No API route receives carrier webhooks yet; a future one must pick the verifier by the number's `carrier_account` and workspace.
- Inbound calls still go through Linedesk's LiveKit SIP; the voice agent and the dispatch do not change (DID → `phone_numbers` row → workspace).
- Warm transfers dial out through the account the called number is in. An `install` number uses the install's `linedesk-outbound` trunk as before. For a `workspace` number the API (never the agent) sets up the outbound side, `apps/api/src/transfer-trunk.ts`: in the workspace's account an object named `linedesk-outbound-<workspace id>` (Twilio: Elastic SIP trunk with a termination domain `linedesk-outbound-<random>.pstn.twilio.com` and a credential list, `createTwilioOutbound`; Telnyx: credential connection and US-only voice profile, `createTelnyxOutbound`), so two workspaces sharing one account never rotate each other's SIP password; and in LiveKit the trunk `linedesk-outbound-<workspace id>-<account fingerprint>` (a hash of the Twilio Account SID or the Telnyx key) with the workspace's own-account numbers as caller IDs. It is set up when a number is connected or released and when the carrier is set (`carrier.set` first deletes the workspace's LiveKit outbound trunks, so a trunk of an old account is never dialled through); carrier and LiveKit requests each give up after 8 s, and a failure is logged without undoing the change. The agent asks `carrier.transferTrunk { from }` (agent token, `x-workspace-id`; the number must be that workspace's) for the carrier and the trunk's exact name and finds it only when the transfer dials; when it is missing, lacks the caller ID, or the carrier refuses its credentials (SIP 401/407, once; not 403, which Twilio also sends for a destination the account may not call), it calls `carrier.provisionTransferTrunk` (under the workspace carrier lock, at most 3 per workspace in 10 minutes), which is logged in the command log and the audit log (kind `keys`, like `carrier.set`). A set-up caused by `phoneNumber.setup`, `phoneNumber.release` or `carrier.set` writes the same audit entry with its trigger. A new set-up creates the new LiveKit trunk before it deletes the old one. No carrier credential ever goes to the agent. A workspace cannot bring the install's own account (same Twilio Account SID or Telnyx key: refused; Telnyx names no account id without a request per key, so another key of the install's Telnyx account is not recognised); when the install's keys cannot be read the check cannot run and saving is refused. A number in a workspace's own account whose account is gone gets no transfer, never the install's trunk. Allowed destinations are the carrier's account setting (Twilio Voice Geographic Permissions); Linedesk checks the on-call number before dialling (US only).

**What the business configures for its own account.** Nothing on the SIP side: Linedesk provisions it through the carrier's API with the credentials.

- Twilio: in the Twilio Console, Account › API keys & tokens, create a Standard API key; enter the Account SID, the key SID and secret (or the auth token instead). Elastic SIP Trunking must be available on the account (it is by default). On "Add number", Linedesk creates (once) an Elastic SIP trunk named `linedesk-livekit` whose origination URI is `sip:<LIVEKIT_SIP_ENDPOINT>;transport=tcp`, and attaches the number to it (a number belongs to one trunk, so a number on another trunk moves to this one). Disconnecting takes the number off that trunk (it then has no voice routing and stops answering until the business routes it again); nothing else in the account is changed. A number bought through Linedesk is bought in, and billed by, the business's account, and released there.
- Telnyx: create an API key (Auth › API keys) and enter it. Linedesk creates (once) an FQDN connection `linedesk-livekit` to `<LIVEKIT_SIP_ENDPOINT>` port 5060 over TCP and assigns the number to it; disconnecting un-assigns it (`connection_id` null) only if it is still on that connection, so it stops answering until the business routes it again; Settings says so before disconnecting. Objects not named `linedesk-*` are never changed.
- Calls and numbers are billed by the carrier to the business; Linedesk does not see the carrier's invoice.

**What the operator does.** `LIVEKIT_SIP_ENDPOINT` must be reachable from the business's carrier (the same public address the install's carrier uses). Like every number today, a newly connected number still has to be added to LiveKit's inbound trunk (`pnpm --filter @linedesk/agent setup-sip <all numbers>`) before calls are accepted. Open point: LiveKit's inbound trunk has no allowed-address or credential list yet, so any SIP source that reaches the endpoint could present any connected number as the dialled number; with several carrier accounts the fix is per-trunk authentication or the carriers' signalling ranges (not built).

**Who may call in (inbound SIP).** LiveKit SIP listens on 5060 for the whole internet, and an INVITE carries whatever caller ID and called number the sender likes. So the inbound trunk `linedesk-inbound` only takes calls whose source IP is one of the carriers' published signaling addresses (`allowedAddresses`); any other INVITE matches no trunk, and since the dispatch rule is bound to that trunk, LiveKit answers 404 and no room, agent or call row is created. The addresses are in one file, `packages/telephony/src/signaling-addresses.ts`, with the source and the date each list was checked: Telnyx's primary and secondary signaling IP of every SIP region (sip.telnyx.com/voice.json), Twilio's Elastic SIP Trunking signaling gateways of every edge (/30 each). LiveKit compares IP entries only with the packet's source address (a hostname entry would be compared with the From host, which the caller sets), so only IPs and CIDR ranges are accepted.

- `setup-sip` applies it on every run: it updates the trunk in place (same id, no gap), creates it if missing, and warns about other LiveKit objects that would still let calls in from anywhere (inbound trunks with neither addresses nor credentials, dispatch rules bound to no trunk). It does not change them.
- **How long and how many calls** (each minute costs speech recognition, the model and the voice on the operator's keys): the assistant says goodbye and hangs up after 25 minutes (`ASSISTANT_CALL_MAX_MINUTES`, a timer in the agent). A call it put through to a person goes on: the inbound trunk ends every call after 2 hours (`maxCallDuration`, `CALL_MAX_MINUTES`; LiveKit only takes it in a whole new trunk, so `setup-sip` writes the trunk back with exactly the numbers and addresses it just set, never fewer), and the on-call leg has the same cap. Silence on the line, per assistant (Settings › Assistant › Advanced; `assistants.silence_first_gap_s`, `silence_reminders`, `silence_closing`; defaults 8 s, 2, the default line): after the first gap with neither side speaking (the session's `userAwayTimeout`) the assistant asks "Are you still there?", again after twice as long, and so on, then says the closing line and hangs up (`remindOnSilence`, `hang-up.ts`; with the defaults: asks at 8 and 24 s, closing at 56 s). A word from the caller starts it over; never during or after a transfer. The assistant always says something before a call ends: end_call without a goodbye of the model's gets "Thanks for calling. Goodbye!", the time limits have their own goodbye (test calls from the web app: 5 minutes), and busy and blocked callers hear one line before the agent hangs up (when the voice is set up). A workspace's assistant answers 5 phone calls at once (`LIVE_CALLS_PER_WORKSPACE`; live phone calls started in the last 30 minutes, counted under a per-workspace advisory lock in `call.start`; test calls have their own limits): the next one is filed as a missed call with a callback and the usual push, `call.start` answers `busy` and `blocked`, and the agent says that all lines are busy and hangs up (an agent of the release before hangs up at once). The stale-call sweep (`stale-calls.ts`) also deletes the LiveKit room of each call it ends, so a line still open is hung up on; a call put through to a person counts as stale only after 2 hours.
- `LIVEKIT_SIP_ALLOWED_ADDRESSES` (default `telnyx twilio`) lists carrier names and/or IPs and CIDR ranges, for BYO SIP or a self-hoster's own PBX; `any` alone turns the restriction off and `setup-sip` warns. Anything else is refused, so a typo never leaves the trunk open (LiveKit itself silently drops entries it cannot parse, and an empty list means open). `setup-sip --print-allowed-addresses` prints the list for a firewall.
- Why IP allowlists and not SIP digest (`authUsername`/`authPassword`) for both carriers: Twilio's trunk origination does not answer a digest challenge. Telnyx delivers to our FQDN connection, and neither the FQDN connection API nor Telnyx's LiveKit guide offers credentials for calls Telnyx sends out (its user name and password are for calls into Telnyx); a Telnyx credential connection only delivers calls to a registered SIP client, and LiveKit SIP does not register. A digest challenge would refuse every real call. The cost of the allowlist: when a carrier adds signaling addresses, calls from them are refused until the file is updated; the carriers announce such changes, and the `checked` dates say when the list was last compared.
- Per-workspace carrier accounts (Twilio or Telnyx) send from the same published addresses as the install's account, so one list covers every workspace; a workspace on another carrier or its own SIP gear needs its addresses added.

US practical notes: outbound needs a SIP trunk; Twilio needs Trust Hub + SHAKEN/STIR for A attestation; warm transfer needs the `linedesk-outbound` trunk (`setup-sip --outbound`, Telnyx for now); a cold transfer would need SIP REFER on the trunk (not used).

**Calendar:**

- Connecting: an owner or admin clicks Connect Google / Connect Microsoft (`calendar.connectStart`, returns the consent URL). The OAuth apps are the sign-in apps (`GOOGLE_*`, `MICROSOFT_*`), but the flow is Linedesk's own, not a Better Auth account link: a linked account would also become a way to sign in. State (32 random bytes, the row id of `calendar_oauth_states`) is bound to the member and workspace, single use, 10 minutes; PKCE S256. The provider returns to `GET /v1/calendar/callback/<provider>` (redirect URI `<BETTER_AUTH_URL>/v1/calendar/callback/google|microsoft`), which runs `calendar.connectFinish` as the signed-in member (the code is redacted in the command log) and redirects to `#assistant/calendar`. Not while impersonating. Sign-in asks for no calendar scope.
- OAuth scopes (asked only when connecting): Google `calendar.events` + `calendar.freebusy` + `calendar.calendarlist.readonly` (not restricted, no CASA audit; never Gmail/Drive), Microsoft `Calendars.ReadWrite` + `offline_access` + `User.Read`. A Google grant without the calendar scopes is refused and revoked.
- A connection (`calendar_connections`: provider, account email, status, who connected it) belongs to the workspace and is synced; its tokens are in `calendar_credentials` (never synced), AES-256-GCM with `SECRETS_KEY`, each ciphertext bound to its connection and kind. An access token with less than a minute left is refreshed on use; Microsoft's new refresh token replaces the old. A refused refresh marks the connection `needs_reconnect`. `calendar.disconnect` deletes the connection, its tokens and its assistant calendars, then revokes the grant at Google (Microsoft has no per-app revoke; the result tells the member where to remove it).
- An assistant books into one or more calendars (`assistant_calendars`: calendar, the owner's instruction for when to use it, enabled, one default). Only calendars the account can write to can be added; the name comes from the provider.
- Availability engine in the API (`apps/api/src/bookings.ts`): the business hours = working hours + exceptions when business hours are switched on (else Monday to Friday 9 to 5 in the workspace time zone); each appointment type is booked inside them, outside them or at any time (`book_when`, `hoursFor` in `packages/calendar`); appointment types (duration, buffer before and after, min notice, max days ahead, location), the chosen calendar's busy times at the provider (one request, 4 s timeout), existing bookings of that calendar. `calendar.findSlots` takes `calendarId` and local `fromDate`/`toDate`; each slot has a spoken `label`.
- Booking on a call: `call.start` returns `booking` (appointment types with their required details, the answering assistant's enabled calendars of connected accounts with their instructions, today in the business time zone, and `canChangeBookings`) or null; then the assistant only takes messages. The agent's tools `find_slots` and `book_appointment` (and `cancel_appointment`/`reschedule_appointment` when `canChangeBookings`) run `calendar.findSlots`, `appointment.book`, `appointment.cancel`, `appointment.reschedule` (permission `calendar:write`: every role; the agent runs `calendar.findSlots` in its call's workspace and the other three only with its `callId`). The model picks the calendar from the instructions; the API checks it belongs to the assistant that answered the call, re-checks the slot under a per-calendar advisory lock, writes the event (title `<Type> · <Caller>`, reason, phone, address, link to the call) and stores the booking; if the transaction fails the event is deleted. Caller ID is a hint, never identity (it is cheap to fake): the agent is never told a caller's bookings (`upcoming` is always empty, kept for older agents). To cancel or move one the caller says its day and the name it is booked under; the agent passes both (`bookingDate`, `bookedName`, never a booking id) and the API finds the one upcoming booking of the call's contact on that day in the business time zone whose name matches (every word of the booked name, in any order, and no other word), or refuses with the same answer whatever was wrong (no booking that day, another name, two matches, or, once found, anything that stops the change: its appointment type switched off, the calendar refusing; that change is rolled back in a savepoint). On reschedule the agent also sends the appointment type and calendar it searched with, and the API checks the new time with them before it looks for the booking, so a taken time says nothing about whether a booking exists. Every refusal is a miss, kept on the call (`calls.booking_misses`; the action succeeds with `changed: false`, so the miss is not rolled back). One caller's changes run one at a time (an advisory lock per contact), so calls at once cannot each pass the check before the other counts. An agent of the release before gets a plain refusal before anything else, since it would read any answer as done: on reschedule when it sends no type and calendar, on cancel when it does not send `readsRefusals`. A new time taken since find_slots is no miss (`slotTaken`): the caller picks another one. At 3 misses in 24 hours over the caller's calls (by contact, or by number without one) booking changes by phone stop for that caller (`canChangeBookings` false at the next `call.start`, every further try refused without counting) and the call that reached the limit is flagged urgent with a next step for the team and an urgent push. The agent also stops after two refusals on one call and takes a message. By id the agent can only change a booking made on the same call (the call test cleans up that way). A withheld or malformed caller ID (not E.164: "anonymous", "restricted", no caller ID at all) gets no contact (such callers would all share one), so no booking changes, no blocking by number, and it is never put on a booking as the phone number. Only bookings made through Linedesk exist. Each appointment type can require phone, email or address on top of name and reason. A booking with an email address queues a confirmation email (pg-boss `booking.confirm`); no SMS yet. The call's outcome is `booked`.
- Contact notes on a call: the contact `call.start` matched (by number; none for a withheld number) comes back with its `note`, and the agent puts it into the assistant's instructions as "Notes your team keeps about this caller" (`callerNotesInstructions` in `apps/agent/src/prompt.ts`): whitespace collapsed, cut at 2,000 characters, between `<caller_notes>` tags. The assistant uses them for context and preferences, never reads them out or confirms them, and treats them as notes, not instructions. Since caller ID is a hint, it does not mention or act on anything private from them until the caller has said the full name on file (no name on file: not at all on that call). The contact's Note field in the web app says which assistant sees it.
- Events: title `<Type> · <Caller>`, description with summary, phone, address and a deep link to the call.
- Sync back: Google `events.watch` / Graph subscriptions update `Booking` when the owner moves or deletes an event.

### Inbox semantics

Views are derived, not stored. They answer one question: does a person still have to act?

- **Needs you:** open calls a person has to act on: live calls, `urgency = urgent`, outcomes `callback | message | hangup`. Priority order inside each day: live, urgent, new-caller callbacks, other callbacks, messages, hang-ups.
- **Handled by Maya:** open calls the assistant finished (`booked | rescheduled | cancelled | answered | transferred`). Skim and clear with E.
- **Spam:** outcome `spam`, kept out of every other view, never deleted silently.
- **Reminders:** calls with `reminder_at` in the future; they return to their view when it passes.
- **Done:** `inbox_state = done`.
- **Search** (`/`) covers all calls, including transcripts.

E marks done (Z undoes), H sets a reminder. The sidebar value counter is `count(calls)`, `count(bookings)` and `count(bookings) × avg_job_value` for the current week.

## 10. Compliance (configurable, not enforced in v1)

US first. Guardrails come once we know the starting states and use cases; the design keeps them easy to add:

- AI disclosure in the greeting: on by default, configurable.
- Recording notice: a workspace setting, off by default, with no per-state logic (Settings, Recordings: "Say that the call may be recorded" and the sentence, default "This call may be recorded."; `workspace_settings.recording_notice_on` / `recording_notice`). `call.start` returns it as `recordingNotice` (null when off or for a blocked caller), and the agent says it right after the greeting, also the outside-hours greeting (`withRecordingNotice` in `apps/agent/src/call-session.ts`); greeting and notice are cached as one audio.
- Outbound-call consent (TCPA), data region: planned; nothing is enforced yet.
- Data retention: recordings (the audio) are kept 90 days by default, per workspace (`workspace_settings.recording_retention_days`, Settings, Recordings; empty keeps them); a daily job (`apps/api/src/recording-retention.ts`) deletes older audio from its store and clears the call's `recording_key`, nothing else. "Don't keep" is `0`: `call.start` returns `keepRecording: false` and the agent does not start egress (the transcript and summary come from live speech recognition, never from the recording); a recording made anyway (an older agent, the setting changed mid-call, one linked by the orphan sweep) is deleted right after `call.setRecording` by the `recording.delete` job (pg-boss, retried with backoff, both stores), and the daily job catches the rest. The call view then says "Recording not kept". Calls, their summaries and transcripts (`transcript_segments`) are never deleted by any job: the only code that deletes calls or transcripts is `pnpm db:seed -- --reset` for the demo workspace, and a transcript goes only with its call (foreign key, `on delete cascade`). `apps/api/test/recording-retention.test.ts` checks that the cleanup leaves the call, summary and transcript.
- Spam scoring uses carrier attestation + number reputation.

**Default `docker compose`:** caddy, app (web + API + MCP), worker, voice agent, postgres, electric, livekit-server, livekit-sip, redis/valkey (needed by LiveKit SIP); optional `recording` profile (livekit-egress writing to a shared directory; no storage server). App, worker and agent are stateless replicas; LiveKit scales via Redis; Postgres can be managed.

**Updates without downtime** (`scripts/deploy.sh`, also what the test server runs after every green main): Caddy (`proxy`, the only published web port) stays up and reaches the API and the web app's files (`web`) by service name, retrying a request on another container for up to 30 s when one cannot be reached. The script builds while the old version serves, then replaces only services whose image or settings changed, start-first: a second `api` (or `web`) container starts next to the old one, and the old one is stopped once the new one is healthy. The voice agent goes the same way: the new worker registers with LiveKit (its health check), then the old one gets SIGTERM, reports itself full, finishes its calls (`stop_grace_period`, 15 minutes) and exits, so there is never a moment without a registered worker and no call is cut off. The agent reaches the API through Caddy too (`http://proxy:3100`). A new Caddyfile is loaded into the running Caddy (`caddy reload`); only a change to its compose settings recreates it (a few seconds without the site).

**Dev mode** (test server only, [dev-mode.md](dev-mode.md)): `LINEDESK_MODE=dev` adds `docker-compose.dev.yml`, which runs `api`, `web` (Vite dev server) and `agent` from the server's git checkout under a watcher instead of from images. An update fast-forwards the checkout (`scripts/deploy-dev.sh`, refused when the checkout has local changes); the API restarts in place in about two seconds while Caddy holds requests, and an agent restart ends its running calls. Production and self-hosting stay on images.

Migrations run once, when the new API container starts, while the old API still serves; the old agent may keep running for up to 15 minutes. So every migration is **expand/contract**: it must work with the code of the previous release. Add (a nullable column or one with a default, a new table, a new index) in one release and start using it; drop or rename (a column, a table, a NOT NULL without a default, a changed type) only in a later release, once no running code reads or writes the old shape. A rename is add-copy-switch-drop across releases.

**Hosted version:** same code, LiveKit Cloud (US), managed numbers, US East region, pass-through minute pricing.

## 12. Admin area and provider keys

For the operator of a multi-tenant install: a view above the workspaces, and the provider keys in the database instead of only in env.

**Instance admin** is a property of the user (`user.instance_admin`), separate from the workspace roles. It adds the permission `instance:admin`, which no role has, in whatever workspace the user is active (and without a workspace). Who gets it:

- the first user of an install, but only when `INSTANCE_ADMIN_EMAILS` lists their address and it is proven (email code or sign-in provider); otherwise nobody gets it automatically, so whoever reaches a fresh install first cannot take it over. The operator lists their address in `INSTANCE_ADMIN_EMAILS` or creates the first admin with `user:create --admin`. With sign-up closed, an empty install accepts only a listed address. (Existing installs keep their admins.);
- anyone an instance admin grants it to (`instanceAdmin.grant` / `instanceAdmin.revoke`; the last enabled instance admin cannot be revoked or disabled);
- addresses in `INSTANCE_ADMIN_EMAILS`, evaluated on every request, so it applies to accounts that already exist, but only once the address is verified (an email-link sign-in or a sign-in provider verifies it). An unverified address grants nothing, and a password sign-up for a listed address is refused: otherwise someone could register the operator's address first and gain admin when the operator later verifies it.

**Second factor for instance admins.** `instance:admin` is granted only to an admin whose email address is confirmed, in a session started by a recent sign-in (`apps/api/src/admin-second-factor.ts`): a passkey sign-in counts for 12 hours (`session.passkey_verified_at`, set by the `session.create` hook on `/passkey/verify-authentication`, `input: false`), any other method (email code, password, Google, Microsoft, GitHub, single sign-on) for 1 hour from the session's `createdAt`, which Better Auth never moves and clients cannot change. Impersonation sessions never carry `instance:admin`. Without it, `GET /v1/admin/*`, the admin actions and `POST /v1/impersonation/start` answer 403 `{ code: "SECOND_FACTOR_REQUIRED", secondFactor: "email" | "confirm" }`, `/v1/me` reports `adminSecondFactor`, and the web app shows the sign-in page with every method of the install in its place ("Sign in again for Admin", `apps/web/src/admin/SecondFactorPrompt.tsx`; an email code also confirms the address). **Passkey step-up** (`apps/api/src/admin-step-up.ts`, checked in `run-action.ts`): what could keep the role or take over passkeys needs a passkey sign-in in the last 12 hours on top, so a stolen mailbox, password or provider account opens Admin but cannot take it over: `instanceAdmin.grant`, `user.resetPasskeys`, `user.impersonate`, `user.invite` with admin, email and sign-in settings (`provider.setKeys`/`clearKeys` of those providers), and any action on an instance admin, the caller included, by `userId` or by workspace `memberId` (disable, enable, revoke, adding them to a workspace, changing their role there or removing them). The dialog names the action it confirms; several waiting at once are answered by one passkey sign-in, and Cancel answers only the one shown. Otherwise 403 `{ code: "PASSKEY_STEP_UP_REQUIRED", stepUp: "confirm" | "enrol" }`; the web app then asks for the passkey in a dialog (`apps/web/src/admin/PasskeyStepUp.tsx`, a passkey sign-in that starts a new session) and runs the action again, or, for an admin without a passkey (`enrol`), points to adding the first with an enrolment code. The handlers that return an enrolment code refuse a session without a passkey sign-in themselves too, and nobody resets their own passkeys (another admin, or `user:passkeys --remove` on the server). The CLI runs as the server operator without a session and needs no step-up. **Alerts** (`apps/api/src/admin-alerts.ts`): every enabled instance admin is emailed when an admin signs in with anything but a passkey or from an address and browser not seen before (the `auth_events` sign-ins), when someone is made admin, and when passkeys are reset. Every admin session that is not a passkey sign-in from a known device is reported, also one from an endpoint the alert does not recognise (as "another method"); the email shows the address and a shortened browser string with links removed. On an install with a single admin the alert goes only to that admin's own mailbox, which is the one an attacker would have: add a second admin, or rely on the passkey step-up. Better Auth's sign-in and linking with a provider ID token posted by the client (`/sign-in/social`, `/link-social` with `idToken`) are refused (`refuseIdTokenSignIn`, auth.ts): Linedesk signs in with providers only through the redirect. The redirect's state is one encrypted, browser-bound cookie that lasts 10 minutes (`account.storeStateStrategy: 'cookie'`, auth.ts). With Better Auth's default, the state was in the database for 10 minutes but also needed a second cookie that lasted only 5, so a slow provider sign-in came back with `?error=state_mismatch`. That error still appears when another provider sign-in was started in the same browser before the first one finished (the newer one replaces the cookie), or after 10 minutes; the sign-in page then says to start again. `ADMIN_SECOND_FACTOR=off` turns all of this off (recency, the email check, the step-up; for installs without https or email) and the API prints a warning at every start. TOTP is not offered.

Better Auth's admin plugin was not used: it adds impersonation, user creation, password reset and its own role system as HTTP endpoints outside the action registry. Impersonation is built on the registry instead (below), with Better Auth's own sessions and cookies.

**Impersonation.** An instance admin can sign in as a user (Admin, Users, the user, "Sign in as …") to see Linedesk as they do. Two registry actions, both in the command log: `user.impersonate` { userId } (`instance:admin`; the actor is the admin) and `impersonation.stop` (permission `impersonation:stop`, which only an impersonated session has; the actor is the user, `commands.impersonated_by` the admin). An action cannot set cookies, so both run only through `POST /v1/impersonation/start` and `/stop` (`apps/api/src/impersonation-routes.ts`); `POST /v1/actions/<name>` refuses them.

- `user.impersonate` refuses yourself, a disabled user, another instance admin (also one by `INSTANCE_ADMIN_EMAILS`) and a session that is itself an impersonation. It creates a Better Auth session for the user with its internal adapter: `session.impersonated_by` = the admin, expiry one hour, active workspace = the user's first. The route sets Better Auth's session cookie to it, signed as Better Auth signs it, and keeps the admin's own session token in a separate signed, httpOnly, SameSite=Lax cookie (`better-auth.admin_session`, Secure on https) for the same hour. The user's last sign-in is not touched.
- The hour is fixed: the session is marked "not remembered" and a `session.update` hook keeps its expiry when Better Auth would extend it; `resolveActor` also refuses it one hour after it started, and as soon as the admin is disabled or no longer an instance admin.
- While impersonating, the actor has the user's workspace permissions plus `impersonation:stop`, never `instance:admin`, so `/v1/admin/*` and admin actions are refused and no second impersonation starts. Registry actions are an allow-list (`IMPERSONATION_ALLOWED_WRITES` in `apps/api/src/impersonation-guard.ts`, checked centrally in `run-action.ts`): read-only actions (except `webhook.test`, `call.lookUpCaller`, `call.askWebhook`, `carrier.test` and `assistant.startTestCall`, which reach outside), inbox triage (`call.markRead/markUnread/markDone/markNotDone/remind/clearReminder`) and `impersonation.stop`; every other write answers 403 "Not possible while signed in as another user.", so nothing done as the user can outlast the hour (no invitations, members, API keys, webhooks, carrier, numbers, assistant or transfer settings). Commands record `impersonated_by`. Refused: Better Auth's endpoints that change credentials or the account's security or hand out tokens (change, set or verify a password, update the profile, change email, delete the user, list or revoke sessions, link or unlink accounts, account tokens; `apps/api/src/impersonation-guard.ts`) `POST /v1/account/password` and `POST /v1/workspaces`; the web app does not mark calls read when an impersonating admin opens them.
- `impersonation.stop` deletes the impersonation session. The route then restores the admin's session from the admin cookie only if that cookie's signature is valid and its session exists, has not expired, is no impersonation and belongs to the admin who started it, who is still an enabled instance admin; otherwise the browser is just signed out. The admin cookie is cleared either way.
- `/v1/me` returns `impersonation: { by, user, expiresAt } | null`. The web app shows a dark bar under every page with whose session it is, who is in it, the minutes left and "Return to admin", which returns to the user's page in Admin. Before starting and stopping, the outbox is sent and the local data of the ending session deleted.

**Command log.** Every non-read-only command is a row in `commands` (`apps/api/src/run-action.ts`), for idempotent replays and the audit log, kept as little as that needs (`apps/api/src/command-log.ts`). Inputs are stored with `sensitive` fields `[redacted]` (provider and carrier keys, invitation ids; the same names in the result's `data` too). Results keep their rows only by id (`rowIds`): a replay reads those rows again and returns them as they are now. Actions marked `logged: 'ids'` keep only ids, numbers and booleans of input and result data, every other value as `[omitted]`: `call.start`, `call.appendTranscript`, `call.finish`, `call.takeMessage`, `call.transfer`, `appointment.book`/`.cancel`/`.reschedule`, `contact.import`, `contact.merge` (only `keepId` and `mergeId`; the merged details are on the contact). Deleting a call or a contact cuts the commands about it (by `callId`, or for a contact `contactId`, `keepId` or `mergeId`, in input or result data; jsonb containment, served by GIN indexes on the unpruned rows) down the same way, in the same transaction. A daily job (`commands.prune`, 03:47; index on `created_at` of the unpruned rows) does the same for every command older than 90 days, except the audited actions (`AUDITED_ACTIONS`: team, admin, keys, integrations), whose inputs the audit log shows; `pruned_at` says when. What stays of every command: who, when, which action, workspace, refused or not, the impersonating admin.

**Audit log.** Admin, Audit log (`GET /v1/admin/audit`, `instance:admin`; `apps/api/src/audit.ts`): who did what, newest first, filtered by kind (sign-ins, sign-in methods, admin actions, team changes, provider keys, signed in as a user), person (email or name), workspace and dates, paged with a cursor. Two sources, merged: the command log (`commands`) for admin actions (`user.*`, `workspace.disable/enable`, `instanceAdmin.*`), team and role changes (`team.*`), provider keys (`provider.setKeys/clearKeys/setActive`; inputs already redacted) and impersonation (`user.impersonate`, `impersonation.stop`, and every action done while signed in as a user), refused attempts included; and `auth_events` for what happens in Better Auth's endpoints: sign-ins and sign-ups with their method (password, email code, passkey, Google, Microsoft, GitHub, OIDC; from the endpoint that created the session, in the `session.create` hook), a provider or password added to an account (`account.create`), passkeys added or removed, password changes and accepted invitations (after-hooks on those endpoints, only when they succeed). Impersonation sessions are not sign-ins. Everyday actions (calls, contacts, settings) are not audit entries. Nothing in either table is ever deleted, and `auth_events` has no foreign keys, so entries outlive the user or workspace they name (the email at the time is kept). When a user is deleted, a database trigger anonymises their `auth_events` (email becomes `deleted`, IP address and user agent are cleared) and keeps the events; transcripts stay as they are. Answering a workspace invitation is refused while impersonating, so every accepted invitation is the user's own. A failed audit write is logged and never blocks the sign-in it describes.

**Disabling.** `user.disable` sets `user.disabled_at`, deletes the user's sessions and blocks new ones (a Better Auth `session.create` hook; the API also refuses a disabled user on every request). `workspace.disable` sets `organization.disabled_at`; `call.start` then rejects calls to its numbers, and its members keep only their read permissions (`*:read`): they can sign in and read, but no registry action that writes (triage, settings, phone numbers) runs for them. `/v1/me` reports `workspace.disabled`. Better Auth's own organization endpoints (invitations, roles) do not check it yet.

**Providers.** The registry in `packages/actions/src/admin.ts` describes each provider: label, category (telephony, speech to text, language model, voice, realtime model, email, sign-in and calendar, recording storage), its fields and which are secret or optional; `apps/api/src/provider-test.ts` holds how to test its connection. Shipped: Telnyx (API key, webhook public key; the default carrier), Twilio (account SID, auth token), Deepgram (API key, model), OpenRouter (API key, model, summary model), OpenAI (API key, model, summary model), ElevenLabs and Cartesia (API key, model, default voice), OpenAI Realtime (API key, model, voice, summary model; its key falls back to `OPENAI_API_KEY`), for email SMTP (URL, from; presets for Postmark, Resend and Amazon SES), for sign-in and calendar Google, Microsoft (with tenant), GitHub and OIDC (discovery URL, client, button label, trusted email domains), and for recording storage Local disk (`file`, no fields) and S3-compatible (`s3`, see below). Each field falls back to the variable the voice agent reads (`apps/agent/src/config.ts`): `DEEPGRAM_API_KEY`, `STT_MODEL`, `LLM_MODEL`, `SUMMARY_MODEL`, `TTS_MODEL`, `TTS_VOICE_ID`, `S3_ENDPOINT` and so on. The database stores provider id and field name as text (`provider_settings`, one row per field), so a new provider is an entry in the registry and no migration. `workspace_id` is null: the keys are for the whole install. Rows with a workspace id are a workspace's own carrier credentials (§8, Own carrier account); they never count for the install, the admin area does not list them, and only `apps/api/src/workspace-carrier.ts` reads them.

**What stays in env.** Only what the install needs before it can read its database: the secrets its containers share (`POSTGRES_PASSWORD`, `ELECTRIC_SECRET`, `BETTER_AUTH_SECRET`, `SECRETS_KEY`, `AGENT_API_TOKEN`, LiveKit's key and secret, which LiveKit, SIP and egress read from their own config), addresses (`PUBLIC_URL`) and limits. `scripts/setup.sh` writes them with random values, so a new install needs no hand-made `.env`. Every provider field keeps its variable as a fallback for scripted installs; `apps/api/src/providers-import.ts` moves set variables into the app.

**Sign-in and email are read at start** (`apps/api/src/instance-env.ts`): Better Auth is built with its sign-in providers and the mail transport once. `server.ts` copies the stored values of the email and sign-in categories into `process.env` (the stored value wins; `serverEnv` keeps the server's own variables, the fallback the admin area shows) and only then imports the app. A change there (`provider.setKeys`/`clearKeys`) needs a passkey sign-in (the step-up below: an SMTP server or sign-in provider of one's own would hand over sign-in codes or any account), emails every instance admin, and restarts the API once it has committed where something starts it again (`LINEDESK_SELF_RESTART=1`, set by `docker/api-entrypoint.sh`: Docker's restart policy, dev mode's runner); every API process also compares the stored rows every 15 s and restarts when they changed, so a second process follows. In `pnpm dev` it logs that a restart is needed. Sign-in (`sign_in`) is the one category where every provider that is set up is in use at once (`multiCategories`); the dialog shows the redirect URIs to add to the provider's app. "Test connection" for an OAuth app exchanges a made-up code: the provider checks the client first (`invalid_client`) and the code second (`invalid_grant`), so a rejected code means the app is right. SMTP is tested by connecting and logging in.

**Push keys** (VAPID) are made on the first start and stored in `instance_settings` (the private key encrypted), shared by every API process; `VAPID_*` on the server win.

**First admin: setup code** (`apps/api/src/setup.ts`). While the install has no user, the API prints a one-time code (8 characters, about 40 bits) to its log at every start and stores its SHA-256 in `instance_settings`. `GET /v1/auth-methods` reports `setupNeeded`; the sign-in page then asks for the code, a name, an email and a password, and `POST /v1/setup` creates the first instance admin and signs them in. Reading the log needs access to the server, so the code proves what `INSTANCE_ADMIN_EMAILS` proves otherwise; the address counts as confirmed, as with `user:create --admin` (there may be no email set up yet). One setup at a time (an advisory lock). Wrong codes are limited to 5 per address and 20 in all per 15 minutes; the code itself stays until the next start, so nobody can rotate it away from the operator. With two API processes starting at once (an update) only the last code printed works. `INSTANCE_ADMIN_EMAILS` and `user:create --admin` keep working.

- Values are encrypted with AES-256-GCM (`apps/api/src/secrets.ts`); the key is `SECRETS_KEY` (32 bytes, base64). Without it, saving is refused with the reason. Losing or changing the key makes the stored values unreadable (the admin area still lists them as set; using them reports the problem): set the keys again.
- Resolution on every use (`apps/api/src/provider-settings.ts`): the stored value wins, the environment variable is the fallback. No restart needed after a change.
- **One provider per category is active.** An instance admin picks it (`provider.setActive`, stored in `instance_settings` as `active_provider.<category>`). Without a pick, the category's variable names it (`TELEPHONY_PROVIDER`, `STT_PROVIDER`, `LLM_PROVIDER`, `TTS_PROVIDER`, `REALTIME_PROVIDER`, `RECORDING_STORE`, as for the agent); without that, each category uses the first provider in the registry with every needed field (telephony: Telnyx before Twilio, and `dev`, no carrier, when none is set up; `TELEPHONY_PROVIDER=dev` keeps it at `dev`). Recording storage and the realtime model have no such fallback (`optInCategories`): the local disk needs no fields and would always count as set up, so calls are recorded only once a store is picked or `RECORDING_STORE` names one; a realtime model answers calls only once it is picked or `REALTIME_PROVIDER` names one, and clearing the pick ("Stop using") goes back to speech to text, language model and voice. While it answers, the voice readiness check needs only it, the cost estimate counts it instead of the three stages, and `voice.options` says `realtime: true`, so the assistant settings hide the voice picker and Transfers. A picked or named provider that is not set up is not replaced by another one.
- A secret never goes back to the browser. `GET /v1/admin/providers` returns per field the source in effect (`app`, `env` or none), the last four characters of a stored secret (none for values shorter than 12 characters or from env), and who changed it when; and per category the active provider. Fields that are not secret (account SID, model, Telnyx public key) are returned in full.
- `provider.setKeys` marks its `values` as `sensitive` in `defineAction`; `run-action.ts` stores sensitive input fields in `commands` as `[redacted]` (keys kept, values dropped). Any new action that takes a secret must do the same.
- `provider.test` makes one authenticated request with an 8 second timeout. On 401/403 the provider's text is not passed on, because providers echo parts of the key; other errors carry the provider's message with every key value removed.

**Recording storage.** Where LiveKit egress writes call audio and the API reads it (`apps/api/src/recording-store.ts`).

- `file`, Local disk: a directory egress and the API share (`RECORDINGS_DIR`; the `recordings` volume with docker compose, `data/recordings` in development). No fields; it stays in env because it is a path on the server. Needs the `recording` compose profile (`pnpm recording:up`).
- `s3`, S3-compatible: endpoint URL, region (default `us-east-1`; `auto` for R2), bucket, access key ID, secret access key (the only secret), optional path prefix and the switch "force path style" (`endpoint/bucket/key`; on by default, off gives `bucket.endpoint/key`). Env fallbacks `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PREFIX`, `S3_FORCE_PATH_STYLE`. The edit form fills in endpoint, region and path style for AWS S3 (`https://s3.<region>.amazonaws.com`), Cloudflare R2 (`https://<account-id>.r2.cloudflarestorage.com`, region `auto`), Hetzner Object Storage (`https://<location>.your-objectstorage.com`), Backblaze B2 and MinIO. The key needs read, write and delete on the bucket.
- The voice agent gets the active store with `GET /v1/agent/provider-config` (`recording`, below) and starts each egress with it: a file path in the shared directory, or an S3 upload with the keys in the request (egress needs no storage settings of its own). It reports the store with the recording (`call.setRecording { store }`), and the API keeps it in `calls.recording_store`.
- Each recording is served, signed and deleted (retention job) from the store it is in, resolved on every use, so switching from the local disk to S3 (or back) needs no restart and older recordings keep playing from where they are. A call recorded before this column existed has `recording_store` null: `RECORDING_STORE` names its store, the local disk without it. S3 settings are not kept per recording: a recording in a bucket plays with the S3 settings in effect, so moving to another bucket means copying the objects (or keeping the old settings).
- `provider.test` for a store writes a small object (`.linedesk-probe-<uuid>.txt`, under the prefix), reads it back and deletes it, with the same 8 second timeout. Errors name the step and S3's status and error code (`NoSuchBucket`, `SignatureDoesNotMatch`); S3's error text is never passed on, because it quotes the key ID, and other text has the key ID and secret removed.
- `workspace.getSettings` reports `recordingOn` from the same setting; the minute sweep that links unreported recordings looks in the active store.

**LiveKit is part of the install, not a provider.** Its URL, key and secret stay in env. `GET /v1/admin/system` reports, read-only, whether the server answers (`ListRooms`) and whether an inbound SIP trunk is configured (`ListSIPInboundTrunk`). The server answers the SIP API without the SIP bridge running, so this shows the SIP setup, not that the bridge is up; the bridge has no API of its own to ask. LiveKit's API does not report a version, so none is shown.

**Admin reads** cross workspaces, so they are plain routes instead of read sync, all behind `instance:admin`: `GET /v1/admin/workspaces`, `/v1/admin/users`, `/v1/admin/usage?months=6` (calls and minutes from `calls.duration_sec` per workspace and UTC calendar month) and `/v1/admin/providers`.

**Agent tokens.** The voice agent has two tokens. The install-wide `AGENT_API_TOKEN` opens a call (`call.start`, which finds the workspace by the dialled number; `call.startTest`, with the workspace from the dispatch the API signed in `x-workspace-id`; `call.findForTest` for the call test) and reads `GET /v1/agent/provider-config`. `call.start` and `call.startTest` return `data.callToken` (`apps/api/src/agent-token.ts`): `ldcall_<payload>.<signature>`, bound to the call's workspace and the call, valid for 4 hours, HMAC-signed with a key derived from `BETTER_AUTH_SECRET` (the agent never has it, so it cannot make one). Every later request about the call goes with it (`apps/agent/src/api-client.ts`); `x-workspace-id` must then be its workspace or absent. A call token runs only the call's actions for its own `callId` and refuses `call.start`, `call.startTest` and `call.findForTest`; the command log keeps it `[redacted]`. The agent role has only the `agent` permission: the `agent` actions plus the member actions marked `agent` in the registry (`calendar.findSlots`; `appointment.book`, `.cancel` and `.reschedule` only with a `callId`), never another member action and never `GET /v1/shape/*` (read sync needs `call:read` and refuses the agent). In a disabled workspace the agent can do nothing, with either token. Updates: an agent older than the API ignores `callToken` and keeps sending the install-wide token with `x-workspace-id`, which this release still accepts for call actions; an API older than the agent returns no `callToken`, and the agent then does the same. This compatibility window ends with the next release, by 2026-12-31 at the latest: it then refuses the install-wide token for everything but opening a call and reading the providers (contract). `GET /v1/agent/provider-config` refuses call tokens (403): a leaked call token never reads the install's keys. Call tokens follow the same entry rule as the install-wide token (internal listener only, checked first) and wrong ones count toward the same per-address throttle.

**Voice agent config.** `GET /v1/agent/provider-config` with the agent token (`Authorization: Bearer $AGENT_API_TOKEN`) returns, per speech and LLM category, for the realtime model (null unless picked) and for recording storage, the active provider and its values in clear, except the recording store's secret fields: the S3 secret access key stays with the API, which starts S3 recordings itself (`call.startRecording`, `apps/api/src/recording-egress.ts`: LiveKit egress gets the bucket's keys in the request; the agent stops the egress and waits for the file with its LiveKit keys as before). An API older than the agent still sends the secret, and the agent then starts the egress itself. The agent token is for the install's own network only: Caddy answers 404 for `/v1/agent/*` on the public site and marks every request it proxies from there with `X-Linedesk-Entry: public` (replacing what the client sent); the API accepts agent tokens only on requests marked `internal`, which Caddy's internal listener (`proxy:3100`) sets and the agent goes through. A request without the header (straight to the API) counts only outside production (`NODE_ENV` not `production`, as in `pnpm dev`); the images set `NODE_ENV=production`, so a container that reaches `api:3100` around the proxy is refused. `call.startRecording` is refused once the call has ended or when its assistant has `record_calls` off; the API holds a lock on the call while it starts egress and returns the egress already recording the room, so a retry never records the call twice. `AGENT_API_TOKEN` must be at least 32 characters: the API refuses to start with a shorter one (the docker entrypoint turns the placeholders `change-me` and the `.env.example` development value off instead), and the agent refuses one too. Wrong agent tokens count per client address: after 10 in 10 minutes the address gets 429 for a while. The agent asks at the start of each call (`apps/agent/src/config.ts`, cached for 30 s per worker process), so an install can come up without keys and start answering once the operator has entered them. For a category that is `null`, or when the API cannot be reached, the agent uses its own env variables; a failure to reach the API is logged once, never with values. Members, instance admins included, get 403. A category is `null` when no provider is set up for it (or the picked one is not); optional fields such as `model` are `null` when unset. 409 `{ ok: false, error }` when stored keys cannot be decrypted. The keys inside a category are the provider's field names from the registry.

```json
{
  "stt": { "provider": "deepgram", "api_key": "…" },
  "llm": { "provider": "openrouter", "api_key": "…", "model": "…" },
  "tts": { "provider": "elevenlabs", "api_key": "…", "model": null, "voice_id": null },
  "recording": { "provider": "s3", "endpoint": "https://….r2.cloudflarestorage.com", "region": "auto", "bucket": "…",
                 "access_key_id": "…", "secret_access_key": "…", "prefix": null, "force_path_style": null }
}
```

`recording` is `{ "provider": "file" }` for the local disk, and `null` when calls are not recorded; then the agent's own `RECORDING_STORE` and `S3_*` apply, as for the other categories (`apps/agent/src/recording.ts`). An agent talking to an API without `recording` does the same.

For `apps/agent/src/config.ts`: `stt.model`, `llm.model`, `tts.model` and `tts.voice_id` are the stored values or the API's environment variables; when `null`, the agent keeps its own defaults (model ids, `baseUrl` per LLM provider). `llm.model` (live turns) and `llm.summary_model` (the summary after the call) are lists, "model, fallback, ..."; with OpenRouter the agent sends the list as `models`, so a rate limit or outage of one model falls through to the next. Defaults: live `google/gemini-2.5-flash-lite, openai/gpt-4.1-mini`, summary `google/gemini-2.5-flash, openai/gpt-5.4-mini`.

**Passwords** (`/sign-in/email`): besides Better Auth's per-IP limit, 10 wrong passwords for one address in 15 minutes, from any IPs, pause password sign-in for it until the window has passed (`sign-in-limits.ts`); other ways in keep working.

**Email sign-in by code.** Better Auth's email OTP plugin (`apps/api/src/auth.ts`): a 6-digit code by email, valid 10 minutes, 3 tries per code (then a new one is needed), stored hashed; at most 3 requests a minute per client address (Better Auth's limit), and per email address and client address 5 codes in 10 minutes and 10 wrong codes an hour (`apps/api/src/sign-in-limits.ts`; only failures count, and counting by address and IP means nobody can lock someone else out by asking for or guessing their codes). The email has the code in its subject and body and no link. A code sign-in marks the address verified. The same flow signs up a new address where sign-up is allowed. Only sign-in codes are sent; the plugin's password-reset and email-change codes are not offered.

**Who is asking.** Rate limits key on the client address, which the API resolves itself (`apps/api/src/client-ip.ts`): the connection's address, or, when the connection comes from a proxy listed in `TRUSTED_PROXIES`, the last `X-Forwarded-For` hop before the trusted proxies. It hands that to Better Auth in its own header, replacing any value a client sent; a client cannot pick its own bucket. Behind another reverse proxy (host Caddy → compose Caddy → API), the compose Caddy keeps the forwarded address only from the ranges in `LINEDESK_TRUSTED_PROXY_RANGES` (`docker/Caddyfile`, `trusted_proxies`); empty by default, so then every client shares the outer proxy's address. Per address, a before-hook allows 5 codes in 10 minutes and 10 sign-in tries an hour across codes; a refused request creates no code and leaves the current one and its tries alone. The plugin's password-reset, email-change and plain-verification endpoints are disabled (`disabledPaths`), and only `sign-in` codes can be requested.

**Closed sign-up.** `AUTH_SIGNUP_ENABLED=false` (`apps/api/src/signup-gate.ts`) refuses every new user in Better Auth's `user.create` hook, which password sign-up, a first code sign-in and a first SSO sign-in all go through. Allowed anyway: the first user of an install, and an address with a pending, unexpired workspace invitation once the address is proven (a code or a sign-in provider; a password sign-up cannot use an invitation). No code is sent to an address that cannot sign in; the answer is the same. Existing users sign in as before. Accounts are made by an instance admin with `user.invite` (Invite user in the admin area, or `pnpm --filter @linedesk/api user:create --email … --name … [--admin]`, which runs the same action as the operator): the account is created unverified and the person gets an email saying how to sign in (with their address and a code from the sign-in page; no code in the invite, since codes expire). Without email delivery the action is refused; if the email cannot be sent, the account is removed again. While sign-up is closed, workspace owners can still invite people into their own workspace (Better Auth organization invitations); that is intended. A provider sign-in refused by the gate goes back to the sign-in page with `?error=SIGNUP_CLOSED` (the hook's error code), not to a bare 403.

**Email confirmation before sensitive actions.** An unconfirmed member (and an API key whose creator is unconfirmed) cannot create API keys, create or update webhooks, invite or re-invite members, change the carrier, set up or change a phone number (forwarding), connect a calendar or turn on the assistant's warm transfer to a number. The registry enforces this centrally with `EMAIL_NOT_VERIFIED`. Password accounts are prompted in the app to confirm a six-digit code. Sending and redeeming that confirmation code requires a session of the same unconfirmed address; wrong confirmation codes count with wrong sign-in codes (per address and IP bucket, `sign-in-limits.ts`); confirmation in that session preserves passwords, keys, webhooks and invitations. Email-code sign-in without that session cleans up unproven access, as provider linking and an email link opened elsewhere do. Not on an install without email delivery (no code could arrive). A password or passkey sign-in whose password or passkeys such a cleanup removed after Better Auth checked them gets no session (a `session.create` hook checks they are still there), and the email link ends every session of the account again after marking it verified (`afterEmailVerification`), so no sign-in under way during the cleanup keeps a way in.

**Sign-in providers and account linking.** Google, Microsoft, GitHub and one OpenID Connect provider, each on when its keys are set (`apps/api/src/auth-methods.ts`; `GET /v1/auth-methods` lists them for the sign-in page). The email address is the account: a provider sign-in lands in the account with the same email, however that account was made (email code, password, an invitation or `user.invite` that never signed in, another provider), and every method attaches to that one account. Condition: the provider proves the address (`apps/api/src/account-linking.ts`). Google: `email_verified`. Microsoft: a personal account (tenant `9188040d-6c67-4c5b-b112-36a304b66dad`: Outlook.com, Hotmail, Live), or a work account whose ID token carries `xms_edov` (the tenant owns the email's domain; an optional claim the app registration must add) or lists the address in `verified_primary_email`; a work account's plain `email` claim is not proof, any tenant can set it. GitHub (`apps/api/src/github-sign-in.ts`, scopes `read:user` and `user:email`): the account's primary address from `GET /user/emails`, only when GitHub verified it; the public profile address and other addresses are never used. OIDC: `email_verified`, or, opted in with `OIDC_TRUST_EMAIL_DOMAINS` (only when the provider sends no such claim), an address on exactly one of the listed domains the provider owns. A sign-in that does not prove its address has no email: Better Auth stops with `email_not_found` before it looks up or creates a user, and the sign-in page says the provider didn't confirm the address. No provider is trusted by name (`trustedProviders` is empty) and `requireLocalEmailVerified` is off, so a proven provider email also joins an account whose own address was never verified; Better Auth then marks it verified, and an `account.create` hook removes what got in without proof (`dropUnprovenAccessOf`: other sign-in accounts, passkeys, sessions, API keys, webhooks, pending invitations, calendar connections) (otherwise someone who signed up with another person's address and a password would keep a way in). The same goes for the email link ("Confirm your email", `/verify-email`): anyone can sign up with another person's address and have the link sent to it, so when the link is opened without a session of that account, a `beforeEmailVerification` hook (`dropUnprovenAccessBeforeEmailLink`, so a failure stops the confirmation) removes everything that got in before the address was proven before Better Auth signs the opener in: every sign-in account (password, providers), passkeys, sessions, push subscriptions, API keys the account created (revoked), webhook endpoints and calendar connections it created and invitations it sent that are still pending, and in the workspaces it owns the assistants' warm transfer (switch and on-call number) and numbers set to forward every call go back to the defaults, recorded in the audit log per workspace as `call_routing_reset` (`dropUnprovenAccessOf`; the provider-link hook drops the same, keeping the provider account it links). Workspaces it created stay, with their members. An unconfirmed address cannot add a passkey at all (403 `EMAIL_NOT_VERIFIED`). Opened in the same browser by the person who signed up, the password stays; opened on another device, they sign in with the link and set a password again. Pending workspace invitations stay pending and can be accepted afterwards. With sign-up closed, a provider sign-in for an address with an account or a pending invitation works; any other is refused with `SIGNUP_CLOSED`. Provider accounts are keyed on the provider's stable id (Google `sub`, Microsoft `oid`, GitHub's numeric id).

**Passkeys.** Better Auth's passkey plugin (`@better-auth/passkey`, `apps/api/src/passkeys.ts`, table `passkey`), on unless `AUTH_PASSKEY_ENABLED=false`; the sign-in page offers "Continue with Passkey" when the server has it on and the browser supports WebAuthn (https or localhost). The relying party is the address people open: its host name is the `rpID` and its origin the only accepted origin, from `PUBLIC_URL`, else `WEB_ORIGIN` (with docker compose both are `PUBLIC_URL`). Changing that address makes existing passkeys unusable (people sign in another way and add a new one). A passkey signs in an existing account only: it is added under Account, Sign-in & security, by a signed-in member whose session is less than a day old (the plugin's fresh-session check), to that member's own account; there is no passkey-first sign-up (`registration.requireSession`, no `resolveUser`), so closed sign-up cannot be bypassed with one. Removing a passkey also needs a session less than a day old (a before-hook; the plugin itself only asks for a session) and works only on the member's own passkeys. Once an account has a passkey, or belongs to an instance admin, passkeys are its second factor (`guardPasskeyChanges`, a before-hook): adding, renaming or removing one then needs a session started by a passkey sign-in in the last 12 hours (`passkeyVerifiedAt`, 12 hours), else 403 `PASSKEY_CONFIRMATION_REQUIRED`, so someone with only the mailbox, the password or the Google account can neither add their own passkey nor remove the real ones. An instance admin's first passkey needs a one-time enrolment code (`apps/api/src/passkey-enrolment.ts`, else 403 `PASSKEY_ENROLMENT_REQUIRED`): `instanceAdmin.grant`, `user.invite` with admin and `user.resetPasskeys` return it once to the admin who ran them (shown in a dialog, `secretResult`, never in the command log), and `pnpm --filter @linedesk/api user:passkeys --enrol --email …` prints it for the first admin of an install or one set by `INSTANCE_ADMIN_EMAILS`. Only its SHA-256 is stored (`user.passkey_enrolment_hash`), it lasts 24 hours and is used up by the first passkey; the browser sends it as `x-passkey-enrolment` with `verify-registration` (asking for options only needs one to be pending), and Account shows an Enrolment code field while `/v1/me` says `passkeyEnrolment`. Non-admins without a passkey keep Better Auth's fresh-session rule. The account is emailed whenever a passkey is added or removed, and both are in the audit log. **Recovery** that needs none of the user's passkeys (a lost device, or a passkey someone else added with the first factor): an instance admin runs Reset passkeys on the user's page (`user.resetPasskeys`, audited; needs `instance:admin`, so never while impersonating): every passkey of the user is removed and all their sessions end in the same transaction (never on the admin's own account), they are emailed (an instance admin always, also with no passkey to remove), and an instance admin gets a new enrolment code. Granting instance admin to someone who already has passkeys lists them with their dates in the dialog, since they become the admin's second factor, and offers "Reset passkeys and make admin" instead. The last admin, or one without a working passkey, does the same on the server: `pnpm --filter @linedesk/api user:passkeys --remove --email …` (runs the same action as the operator). `ADMIN_SECOND_FACTOR=off` is not needed for any of this. A disabled user's passkey creates no session (the `session.create` hook). While impersonating, passkeys cannot be added, renamed, removed or listed (`impersonation-guard.ts`).

**Caller languages.** Settings › Assistant › Advanced › Languages sets `assistants.languages` (`{ main, mode, allowed }`, `packages/actions/src/languages.ts`): a main language (`main`, missing: English) and the languages besides it, `english` none (the name is from before the main language could be picked), `allowed` the picked ones, or `any` every supported one (`LANGUAGES`: English, Spanish, French, German, Italian, Portuguese, Dutch, Russian, Hindi, Japanese, the set Deepgram's multilingual models recognize). English only keeps the configured speech model; any other main language or other languages allowed swap it for the multilingual model of the same family (`createStt` in `apps/agent/src/pipeline.ts`: `flux-general-multi` with a `language_hint` of the call's languages, or Nova-3 `multi`), same price per minute and the same turn detection. The voice starts in the main language (`createTts`) and follows each final transcript's detected language when it is allowed, else goes back to the main one (`followCallerLanguage`, `apps/agent/src/caller-language.ts`); the prompt (`languageInstructions`) and the collection steps (`collectLanguageRule`) say the same. The fixed lines are translated in code for every supported language (`packages/actions/src/spoken-lines.ts`): the greeting and busy lines in the main language, the lines during the call (still there?, goodbye, call limit, the ready replies after take_message and flag_urgent) in the language spoken at that moment, the AI note and consent question (`greetingWithDisclosure`) in the main language. Owner-written texts stay as written; one that is still the English default (the greeting the app wrote, the returning-caller line, the closing line, the recording notice) is said as the main language's default (`inMainLanguage` in `apps/agent/src/call-session.ts`), and the settings page swaps such defaults in the draft when the main language changes (`withMainLanguage`). The team's language stays English: the summary is written in English and starts with "Call in <language>." when the call was not in English, messages and notes saved with tools are in English, the transcript keeps the language spoken. Needs a multilingual voice model (ElevenLabs Flash v2.5, the default, or Cartesia Sonic).

**Assistant voices.** Settings › Assistant › Voice picks `assistants.voice` (`{ provider, voice_id }`; empty id: the install's default voice, `TTS_VOICE_ID` or the provider's). The page lists the suggested voices (the curated ones and the workspace's clones) as compact rows with a play button, and under More voices every voice of every text-to-speech provider that has a key (`voice.catalog`, `apps/api/src/voice-catalog.ts`: each provider's list read with the install's key on the server, kept 5 minutes per provider and key, with search and filters for provider, language, gender and accent). The catalog leaves out other workspaces' clones (live or released) and every clone the account itself made (ElevenLabs instant and professional clones) that Linedesk did not make for this workspace (no consent record); the provider's own voices, designed voices and voices added from ElevenLabs' Voice Library stay (a library copy: `is_owner` false, `sharing.status` `copied` with an `original_voice_id`; its consent is the library's sharing terms; a copy whose owner stopped sharing, `copied_disabled`, is left out). Provider-hosted samples are fetched only from the provider's sample host (`SAMPLE_HOSTS`, ElevenLabs: storage.googleapis.com), at most 2 MB, checked while streaming. A voice of another provider than the one in effect works too: the agent gets every voice provider with a key (`tts_providers` in `GET /v1/agent/provider-config`) and uses the assistant's provider when it has one (`ttsFor` in `apps/agent/src/pipeline.ts`), else the default voice. An assistant may only get the default, a curated voice, a voice of the catalog (`curatedVoices` in `packages/actions/src/voices.ts`: six American English ElevenLabs default voices; none for Cartesia yet) or a voice its own workspace cloned: `assistant.update` checks it on the server (`checkAssistantVoice`). `voice.options` lists them and whether the workspace can clone. Previews: `GET /v1/voices/preview/<voiceId>` (`apps/api/src/voices.ts`) says a fixed sentence in that voice, only for those voices. The curated voices' samples ship with the app (`apps/api/assets/voice-previews/<provider>/<voiceId>.mp3`, made with `PREVIEW_TEXT`; make them again when it changes), so they play without a provider key and never call the provider; a catalog voice plays the sample its provider hosts (ElevenLabs `preview_url`, fetched by the API, free, no hourly limit; `?provider=` names a provider other than the one in effect); any other sample is synthesized once per provider, model, voice and sentence and kept on disk (`VOICE_PREVIEW_DIR`, default the system temp dir; the newest 300 kept), browser-cached for a week; at most 20 new samples per workspace an hour (per API process). The Default voice row plays the voice the install's default stands for (`installDefaultVoice`: the provider's voice id setting, else the voice agent plugin's own default, `providerDefaultVoices`); `voice.options` returns it as `defaultVoice` and the preview endpoint allows it. The picker fetches a sample before playing it, so a refusal shows its reason (no provider: "Add a voice provider key in Admin › Providers to hear samples.") instead of a generic error. **Cloning** is off until an instance admin turns it on (Admin › System, `voiceCloning.set`, `instance_settings.voice_cloning`), and only for providers in `cloningProviders` (ElevenLabs instant voice cloning). `voice.clone` (`settings:write`) takes a recording (≤ 10 MB; the request body is capped before it is read, every other action at 4 MB), checks its first bytes against the claimed type, and calls the provider before the transaction (a `Preparer`, `handler-context.ts`; the clone is deleted again if the command does not commit). It stores a consent record in `voice_clones` (who confirmed, when, the exact statement `CLONE_CONSENT_TEXT`) and makes the voice the assistant's; the recording is not stored (`sensitive`, not in the command log either). A clone no assistant of its workspace uses any more (voice changed, assistant deleted, workspace deleted) is deleted at the provider by the `voice.delete` job and marked `deleted_at` here; the row stays as the consent record and the voice can no longer be picked. Vendor HTTP is in `apps/api/src/voice-provider.ts`.

## 13. Integrations: API keys

A workspace's own integrations (REST, later MCP and webhooks) authenticate with a workspace API key (`apps/api/src/api-keys.ts`).

- Owners and admins create (`apiKey.create { name, role }`), list (`apiKey.list`) and revoke (`apiKey.revoke`) keys under Settings, Developers. A key is `ld_` + 32 random bytes (base64url), shown once in the result of `apiKey.create`; the command log stores that result without it (`secretResult`). Only its SHA-256 hash and its first 11 characters (to tell keys apart) are stored, in `api_keys`, which is never synced.
- `Authorization: Bearer ld_…` on `/v1/actions/<name>` and every other `/v1` read. The actor is `apikey:<id>` in the key's workspace with the key's role (`member` or `admin`, never owner), without `team:write`; keys never manage keys. The agent's `x-workspace-id` header does not apply. A revoked key, or one of a deleted or disabled workspace, is refused (401). A key is checked against its creator on every request: once they are removed from the workspace, disabled by an instance admin, or hold a lower role than the key (an admin key of someone demoted to member), the key is refused; it works again if that is undone, until it is revoked. `last_used_at` is written at most once a minute.
- 300 requests a minute per key (in-memory sliding window per API process), then 429 with `retry-after: 60`.
- Refused `ld_` keys count per client address (`client-ip.ts`): from the 20th in 10 minutes, refused keys from that address get 429 with `retry-after: 600`. From then on only a key that worked in the last 24 hours (kept in memory by its hash) is looked up from that address, so a working integration behind a shared address is not locked out by another host there, and random keys from it cost no database query. A key that never worked before cannot start from a throttled address until it ages out.

## 14. Call evaluations

After a phone call is finished (`call.finish`), a job (`call.evaluate` in pg-boss, `apps/api/src/evaluations.ts`) asks the language model in effect (Admin, Providers) how the assistant handled it: one short request (`max_tokens` 300, the provider's cheap default model unless one is set) with the business instructions, the fixed call rules (`CALL_RULES`), transcript and summary. The answer is a score from 1 to 5 and at most three issues, stored in `call_evaluations` (not synced; one row per call, replaced on a new evaluation). Test calls are evaluated only when asked (`call.evaluate` from the call view). Owners and admins (`settings:write`) read them with `call.getEvaluation` and `call.listEvaluations`: a card under the summary, and the Needs review mode of the inbox (G R) lists calls scored 3 or lower. Without a language model nothing is evaluated.

## 15. Knowledge

What an assistant knows about the business: Settings › Assistant › Business info. Rosie's and fonio's shape (research/competitors-smb.md §2.11), local-first and with no new paid service.

- **About the business** is the assistant's free-text instructions (`business_profile.instructions`; the same at any hour: after-hours behaviour comes from the outside greeting, the call rules and the transfer rules' "only during business hours"), part of the assistant draft and saved with `assistant.update`. Services, prices and common answers are written in it. Services and prices lists, FAQs and documents were removed (2026-11-12): migration 0066 folded stored lists into the About text, the agent no longer reads them, and `knowledge_documents` / `knowledge_chunks` are dropped in a later release (with the originals left in the recording store). The older structured fields (`description`, plain `services` names, service area, address, hours) still stand in for an empty About text.
- **Write with help** (button next to About the business; `knowledge.import`, read-only, `settings:write`, 10 an hour per workspace, refused while impersonating): a three-step wizard asks what the business does (trade, offer, area), optionally its website, and what the assistant should do (take messages, book jobs, handle emergencies, answer prices and common questions, screen spam, plus free text). With a website it reads the home page and up to five same-site pages it links to whose path or link text names services, prices, about, contact, FAQ or areas (`apps/api/src/site-import.ts`), after robots.txt (our group `LinedeskBot`, else `*`; longest rule wins; checked before any page). Fetches go through the webhook guard (`apps/api/src/public-fetch.ts`: http(s) on 80/443 only, no credentials in the URL, every resolved address public via `publicLookup`, redirects followed by hand and checked again, 8 s and 1.5 MB per page; `WEBHOOK_ALLOW_PRIVATE_URLS` lifts it for development). One request to the language model in effect (Admin › Providers; up to 3,000 tokens) gets the owner's words between `<owner>` tags and the page text (scripts and styles dropped, JSON-LD kept, at most 40,000 characters) between `<page>` tags, never to be followed as instructions; the answer (an About text with the services, prices and common answers the owner or the pages give, and up to 8 "When a caller …" use cases) is checked and cut to the limits. Nothing is saved: the last step shows a word diff for a different About text (unpicked by default) and the use cases to pick; picked use cases are added to About the business under "Common calls", and everything goes into the draft, saved with Save.
- **On a call** the prompt (`apps/agent/src/prompt.ts`) has the About text and a fixed price rule (unless the owner turned it off in the checklist): only prices the business gave, exactly as written; anything else gets no price or estimate, the team calls back.
- **Questions the assistant could not answer**: the call evaluation (§14) also returns up to three general questions the caller asked that the assistant could not answer. They are stored in `knowledge_questions` (synced; skipped when already asked on that assistant; at most 30 open per assistant) and listed at the top of Business info, with a quiet line above the inbox for owners and admins. `knowledgeQuestion.answer` adds `If a caller asks "…": …` to the About text in the same transaction (assistant row locked; refused when the text would pass its limit); `knowledgeQuestion.dismiss` closes it.

## 16. Assistant versions

Save is live: there is no separate publish step. Every save that changes what callers get becomes a version (`assistant_versions`, not synced; `apps/api/src/assistant-versions.ts`, shared parts in `packages/actions/src/assistant-versions.ts`): a whole copy of the assistant's call settings (the columns in `VERSIONED_FIELDS`: name, greetings, AI disclosure, style, checklist, about, transfer contacts, voice, languages, silence, recording) and its calendars with their notes, numbered per assistant, with who saved it and a short summary of what changed. The actions in `VERSIONED_ACTIONS` (`assistant.update`, `assistantCalendar.*`) run inside `withVersion`: the settings before the change are kept as a version first (an assistant from before versions gets "Settings as they were"), and the result becomes the next one when it differs (key-sorted JSON, numbers taken under a per-assistant advisory lock). `assistant.create` stores version 1. A call stores the version it ran with (`calls.assistant_version`, set by `call.start` and `call.startTest`; a change that skipped versioning, e.g. from an older release during an update, becomes a version of its own first); the call view shows "Assistant version N".

Settings › Assistant › History (`assistant.versions`, `assistant.version`, read-only, `settings:write`) lists the versions and compares one with now, line by line per part. `assistant.restoreVersion` writes the version's settings back with the same checks as `assistant.update` (voice usable, transfer numbers not Linedesk numbers, a confirmed email to put calls through to a number) and is itself saved as a new version ("Restored version 7"), so a restore is undone by restoring the one before. Calendars are matched by account and calendar id: one no longer connected is left out and named in the result, one added since is switched off. Appointment types, hours and notifications are workspace settings and are not versioned. Restore waits while the form has unsaved edits.
